# إصلاح عملية التسجيل — أعمدة legacy قديمة في profiles (2026-10-05)

## المشكلة (مؤكدة بفحص حي)
كل تسجيل جديد يفشل خادمياً قبل إنشاء المستخدم:

```
POST /auth/v1/signup → 500
{"code": "23502",
 "message": "null value in column \"public_key\" of relation \"profiles\"
             violates not-null constraint"}
```

## التشخيص
- التطبيق سليم: يرسل `username` + `emailRedirectTo` ويعالج حالة
  «انتظار تأكيد البريد» (جلسة null) بشكل صحيح
  (`lib/features/auth/auth_screen.dart` يعرض «تم إنشاء الحساب — أكّد
  بريدك الإلكتروني ثم سجّل الدخول»).
- `supabase/schema.sql` (الحالي) لا يعرّف `public_key` في profiles أصلاً.
- قاعدة البيانات الحية ما زالت تحمل أعمدة legacy من مخطط قديم سابق لإعادة الهندسة
  (`public_key text NOT null` وغيرها)، بينما مشغّل
  `on_auth_user_created → handle_new_user()` يُدخل أعمدة المخطط الحالي فقط —
  فتنكسر قيد NOT NULL ويفشل كل تسجيل.
- قسم الترحيل في schema كان أسقط أعمدة legacy قديمة من `messages` فقط
  وأغفل `profiles`.

## الإصلاح — خطوة مالك واحدة (دقيقتان)
1. افتح لوحة Supabase → **SQL Editor** → **New query**.
2. الصق محتوى الملف كاملاً:
   `supabase/patches/2026-10-05-fix-signup-profiles-legacy-columns.sql`
3. **Run**. ستظهر رسائل `dropped legacy column: …` ثم جدول بأعمدة
   profiles بعد الإصلاح — يجب أن تكون **الأعمدة السبعة للمخطط الحالي فقط**:
   `id, username, display_name, avatar_path, bio, created_at, updated_at`.

> الرقعة آمنة وقابلة لإعادة التشغيل: تُبقي أعمدة المخطط الحالي حصراً (قائمة
> بيضاء) وتُسقط أي شيء آخر، ولا تمس أي صفوف بيانات.
> (إسقاط عميلة غير موجودة = لا شيء.)

## التحقق بعد التشغيل
```bash
bash scripts/probe_signup.sh
```
النتيجة المتوقعة:
```
SERVER-OK — user: xxxxxxxx | identities: ['email'] | session: false
confirmation_sent_at: 2026-10-05T…
```
ثم اختبار حقيقي من التطبيق: تسجيل ببريد حقيقي → رسالة
«تم إنشاء الحساب — أكّد بريدك الإلكتروني ثم سجّل الدخول» → رسالة
البريد (القوالب الافتراضية الإنجليزية كافية وظيفياً لأن التطبيق يمرر
`emailRedirectTo` صراحةً إلى موقع التحقق) → التأكيد من صفحة
confirm.html → تسجيل دخول ناجح.

- **التحقق الحاسم النهائي على مستوى الخادم: VERIFIED** — بعد تجدد

  - `id: 48a343af-4312-45b2-95c9-df400adf53d0` — المستخدم أُنشئ فعلاً

  - `confirmation_sent_at: 2026-10-05T09:16:01Z` — بريد التأكيد
    قُبل للإرسال فعلياً
  - `identities: ['email']` + `user_metadata.username` صحيح +
    `session: null` (تأكيد البريد إلزامي — سلوك متوقع)
- ملاحظة قيّمة من الفحص: Supabase صار يرفض نطاق `example.com` بـ
  `400 email_address_invalid` (تحقق من قابلية التسليم) — لذا
  يستخدم السكربت نطاقاً حقيقياً. وGoTrue في وضع «التأكيد إلزامي»
  يعيد كائن المستخدم في المستوى الأعلى من الاستجابة دون مفتاح
  `user` مُغلِّف.
- الحاجز التشغيلي الوحيد المتبقي: **429 over_email_send_rate_limit**
  — حصة إرسال البريد المدمج المجاني في Supabase (ضئيلة، تتجدد كل
  ساعة تقريباً). لا تعطل التسجيل؛ لا تمنع سوى إرسال رسائل إضافية
  عند استنفاد حصة الساعة.
- **دين إنتاج موثق**: SMTP مخصص (الخطوة ج في EMAIL_SETUP.md) يرفع
  الحصة ويجعل البريد موثوقاً — لا يزال **NOT IMPLEMENTED**.
- ما تبقى للمالك فقط (يتطلب صندوق بريد حقيقي، لا يمكن أتمتته من
  هنا): استلام الرسالة فعلياً في صندوق الوارد ← فتح رابط التأكيد ←
  وصوله إلى confirm.html ← تسجيل الدخول. كل ما قبله مُثبت حياً.
