## ملخص سريع — ما المشكلة وما الحل؟

| البند | قبل | بعد |
|---|---|---|
| رسالة التأكيد | قالب Supabase الافتراضي (إنجليزي، بلا هوية) | 4 قوالب عربية بهوية DRS NEXORA (`docs/email-templates/`) |
| هبوط رابط البريد | على Site URL الافتراضي = صفحة فارغة/مكسورة | صفحات تحقق مستضافة ومخصصة (نجاح/خطأ/تعيين كلمة مرور) |
| استعادة كلمة المرور | لا صفحة لاستقبال الرابط | صفحة `reset.html` بنموذج كامل وتحقق قوة |
| تمرير `emailRedirectTo` من التطبيق | غير موجود | مُضاف في الكود (يشحن مع البناء القادم) |

**نقطة تصميم مهمة:** القوالب الجديدة تبني رابط التحقق صراحةً بـ `{{ .TokenHash }}` وتمرر
`redirect_to` إلى صفحاتنا — لذلك **الإصلاح يعمل فوراً حتى مع النسخ المثبتة حالياً على
الأجهزة (مضمّنة في v0.1.0) دون إصدار APK جديد**.

## 1) أين تُستضاف ملفات موقع التوثيق؟

**الجواب: على GitHub Pages، عبر مستودع عام مخصص:**

- **الرابط المباشر للموقع:** https://cto-drs.github.io/nexora-verify/
- **مستودع النشر (عام):** `CTO-DRS/nexora-verify` — https://github.com/CTO-DRS/nexora-verify
- **مصدر الملفات (الحقيقة الأولى):** داخل مستودع التطبيق نفسه في مجلد `verification-site/`
  لضمان تتبع كل تغيير مع باقي الكود.
- **سكربت النشر:** `scripts/deploy-verify-site.sh` — ينسخ من `verification-site/` إلى المستودع
  العام ويدفع، وPages يبني تلقائياً خلال دقيقة.

| الملف | الوظيفة |
|---|---|
| `index.html` | صفحة هبوط + توجيه تلقائي حسب نوع العملية القادمة في الرابط |
| `confirm.html` | تأكيد التسجيل (signup) وتأكيد تغيير البريد (email_change) |
| `reset.html` | تعيين/إعادة تعيين كلمة المرور (recovery) وكلمة مرور الدعوات (invite) |
| `assets/nexora.css` | الهوية البصرية — نفس ألوان `lib/theme/app_theme.dart` |

لماذا GitHub Pages تحديداً؟ مجانية بالكامل، HTTPS جاهز، CDN عالمي، ولا تحتاج
أي خادم أو بطاقة — والتحديث عبارة عن `git push` واحد. (البدائل: Netlify/Vercel
ممكنة لاحقاً بنفس الملفات دون أي تعديل).

## 2) خطوات لوحة Supabase (مطلوبة من المالك — مرة واحدة)

> هذه الخطوات تحتاج صلاحيات لوحة تحكم Supabase ولا يمكن تنفيذها من خارجها
> (المفتاح المتوفر في التطبيق هو publishable فقط، والقوالب تُدار من اللوحة).

### الخطوة أ — إعداد الروابط المسموحة

افتح: **Supabase Dashboard → مشروعك → Authentication → URL Configuration**

1. **Site URL** — غيّره إلى:
   ```
   https://cto-drs.github.io/nexora-verify/
   ```
2. **Redirect URLs** — اضغط «Add URL» وأضف الثلاثة التالية (كل واحد على حدة):
   ```
   https://cto-drs.github.io/nexora-verify/
   https://cto-drs.github.io/nexora-verify/confirm.html
   https://cto-drs.github.io/nexora-verify/reset.html
   ```
3. اضغط **Save**.

### الخطوة ب — لصق القوالب الأربعة

افتح: **Authentication → Emails → Templates** — ستجد قائمة القوالب على اليسار.
لكل قالب: افتحه → امسح محتوى حقل **Body** → الصق محتوى الملف المقابل →
اكتب الموضوع في حقل **Subject** → اضغط **Save**.

| القالب في اللوحة | الملف الجاهز | حقل الموضوع (Subject) |
|---|---|---|
| **Confirm signup** | `docs/email-templates/01-confirm-signup.html` | `فعّل حسابك في DRS NEXORA` |
| **Reset password** | `docs/email-templates/02-reset-password.html` | `إعادة تعيين كلمة مرور DRS NEXORA` |
| **Invite user** | `docs/email-templates/03-invite-user.html` | `دعوة للانضمام إلى DRS NEXORA` |
| **Confirm email change** | `docs/email-templates/04-email-change.html` | `تأكيد بريدك الإلكتروني الجديد — DRS NEXORA` |

لا تعدّل شيئاً داخل `{ { .TokenHash } }` أو `{{ .Email }}` — هي متغيرات يملؤها
الخادم تلقائياً عند كل رسالة.

### الخطوة ج — (موصى به بشدة للإنتاج) SMTP مخصص

مُرسل البريد المدمج في Supabase مخصص للاختبار فقط: حدود إرسال صارمة جداً
(بحدود 2-4 رسائل/ساعة في الخطة المجانية) وقد تهبط الرسائل في مجلد
الغير مرغوب. للإنتاج:

1. أنشئ حساباً لدى مزود بريد (Resend أو Mailgun أو Brevo — لها خطط مجانية كافية).
2. تحقق من نطاقك (أو استخدم نطاق المزود في البداية).
3. في اللوحة: **Project Settings → Authentication → SMTP Settings** → فعّل
   Custom SMTP → أدخل Host/Port/User/Password من المزود → **Save**.

ما دمت على المُرسل المدمج، التصميم أعلاه يعمل لكن بحدود الإرسال نفسها.

## 3) اختبار ميداني (٥ دقائق)

1. من التطبيق (أو زر «إنشاء حساب»): سجّل بريداً حقيقياً لك.
2. افتح البريد — يجب أن تصلك رسالة عربية بهوية DRS NEXORA وبزر «تفعيل الحساب».
3. اضغط الزر — يجب أن تفتح صفحة بنفسجية داكنة تعرض **«تم تفعيل حسابك بنجاح ✓»**
   مع خطوات الدخول للتطبيق.
4. افتح التطبيق وسجّل الدخول — يجب أن ينجح.
5. اختبار الاستعادة: شاشة الدخول → «نسيت كلمة المرور؟» → رسالة → زر →
   صفحة تعيين كلمة مرور → احفظ → سجّل دخولك بالجديدة.
6. اختبار الخطأ: افتح رابط التفعيل مرتين — المرة الثانية يجب أن تظهر
   صفحة خطأ عربية واضحة بدل الشاشة الفارغة.

## 4) ملاحظات أمنية

- الصفحات المستخدمة تستخدم مفتاح **publishable** فقط (عام بطبيعته مثل مفاتيح
  Firebase العامة) ولا يوجد أي سر في المستودع العام.
- الصفحات لا تخزن جلسات على النطاق (`persistSession: false`) وتُزيل الرموز من
  الرابط بعد الاستخدام.
- لا تشارك روابط التحقق؛ كل رابط يعمل لحساب واحد ولمرة واحدة (One-time OTP).
- حدود المعدل الافتراضية على نقاط التحقق تُبقي الباب مغلقاً أمام التخمين.

## 5) ماذا يوجد في كود التطبيق من هذا الإصدار؟

- `lib/core/config/app_config.dart`: ثابتا `emailConfirmRedirectUrl` و
  `emailResetRedirectUrl`.
- `lib/services/auth_service.dart`: `signUp` يمرر `emailRedirectTo` و
  `resetPasswordForEmail` يمرر `redirectTo` — طبقة أمان إضافية تعمل حتى لو
  نُسي تحديث قالب ما، وتُشحن في **البناء القادم**.

أما النسخ المثبتة حالياً فلا تحتاج تحديثاً: القوالب الجديدة تحمل التوجيه
داخلها، وهذا هو سبب اعتماد رابط `{{ .TokenHash }}` الصريح بدل
`{{ .ConfirmationURL }}` الذي يعتمد على إعدادات العميل.
